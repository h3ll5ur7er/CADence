Reported by an agent modelling a keyboard enclosure through the MCP server (`cadence.exe mcp`, 2026-10-19/20, projects *KB enclosure* and *KB enclosure simple*), report 2.

Inserting 10 instances into the assembly *Keyboard* (two with modelled M8 threads) and then `check_assembly` did not answer within 1800 s; meanwhile `list_projects`, `list_documents` and `get_assembly` hung too (one core at 100 %, 2.8 GB). The insert never reached the document. With the threads as markers the check takes seconds: probably the thread-against-thread interference.

- [x] Requests that need no geometry answer while the kernel is busy
- [x] A long request can be cancelled (MCP `notifications/cancelled`), which stops the kernel and starts a new one
- [x] Progress notifications for long checks
- [x] Find why interference of two modelled threads takes so long, and make it fast (or bounded)
- [x] Test: list_projects answers while a geometry request is running; a cancelled request stops it

Done in phase 33: the MCP server runs the kernel in a Node geometry worker, answers requests side by side, stops the worker on `notifications/cancelled` (no answer for the cancelled call) and reports `check_assembly` progress part by part. The half hour could not be reproduced: the check of the keyboard assembly takes 23 s with thread markers and 72 s with modelled threads here; cancelling now bounds it.
