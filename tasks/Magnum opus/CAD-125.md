title: Drawing a part with a modelled thread blocks the process for minutes
type: bug

Drawing the radial engine's parts ([[CAD-96]], round 5), the spark plug (a modelled M10 thread, [[Magnum opus]]) made every new process that opened its drawing hang. A script or the command line never got past `cadence.drawing(id)`, at 100 % of one core with flat memory, and timers and output stopped too.

- Pausing the main thread from a worker (inspector `connectToMainThread`, `Debugger.pause`) showed it inside the kernel's hidden-line removal: `HLRBRep_InternalAlgo.Hide` ← `makeProjectedEdges` ([[src/core/engines/modeling/drawing-view.ts#L80]]) ← `drawingView` ← `drawView`.
- One iso view of the spark plug alone, in a new drawing in a new process, took **452.6 s**. The plug's drawing has four views (one a section), so opening it takes about half an hour.
- Earlier the same day, new processes drew the same four views in seconds (laying out the sheet, listing anchors, adding dimensions). Nothing in the spark plug's document or result changed in between, so the time depends on some state, or HLR on the thread is not deterministic.
- The MCP server, which had drawn the views before, kept answering at once (it holds the drawn views). Any other client blocks; the app presumably freezes the same way when it opens that drawing (not checked).

Other drawings of the engine open in a new process in 0.2 to 2.6 s (tappet, wrist pin, crank gear and piston timed; all 27 others exported in one run).

- [x] Find why HLR on the thread is sometimes fast and sometimes minutes (triangulation present or not, tolerance, the exact versus the polygonal algorithm)
- [x] Hidden-line removal off the main thread (a worker) or in slices, so a slow view does not freeze the process; views show *Drawing…* meanwhile
- [x] A time limit per view, falling back to a polygonal projection (`HLRBRep_PolyAlgo`) with a note on the view
- [x] Drawn views cached with the drawing (by source result and view), so a new process does not draw them again
- [x] Test: a drawing of a part with a modelled thread opens in a new process within seconds

Fixed in phase 30 ([[Architecture/Decisions#ADR-49]]). Why: not a state but the direction. The plug's *top* view, along the thread's axis, takes 462.7 s in the kernel's exact hidden-line removal (measured on a copy of the engine: front, right and iso take seconds, the section 0.7 s; the same top view tilted by 0.02 rad takes seconds). The earlier quick runs drew the other views. Triangulation and the result bytes make no difference (the live result and a fresh one both draw the iso view in 3.8 s). The kernel build has no `HLRBRep_PolyAlgo`, so the fallback is our own: [[src/core/engines/modeling/hidden-lines.ts]] decides from a depth picture of the triangles what is seen along each edge and outline (exact edges and cylinder outlines where wholly seen or hidden); the plug's top view takes 0.9 s that way. Views are drawn exactly in a views worker of their own ([[src/workers/views.worker.ts]]; a Node worker of the same module for scripts and the MCP server), stopped after 20 s (`stoppable` in [[src/core/utilities/messaging/rpc.ts]]); the view is then drawn from the triangles with a note. The sheet is laid out first with *Drawing…* for views still being drawn. Drawn views are kept as the drawing's result, so another process opens the drawing at once. Checked on a copy of the spark plug's drawing (four views): 45 s in a new process the first time, the main thread running throughout (its timer ticked 44 times), then 0.1 s. Tests: the time limit and the cache in [[src/core/managers/drawing/drawing-manager.spec.ts]], the mesh projection in [[src/core/engines/modeling/drawing-view.spec.ts]], `stoppable` in [[src/core/utilities/messaging/rpc.spec.ts]].
